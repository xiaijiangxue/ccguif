# Output Timeline Operation Flow

---

## Summary

将对话输出区里的连续工具调用从并列卡片堆叠改为“时间轴操作流”。默认视图只保留用户扫读任务进展所需的信息：当前正在做什么、哪些动作已经完成、哪里失败、最终产出了什么；细节内容作为按需展开的证据层保留。

这个重构的目标不是让卡片更漂亮，而是减少杂乱、突出重点，并降低长任务中大量工具节点同时渲染造成的感知卡顿。

---

## Problem Frame

当前输出区在连续工具调用、多 agent 长任务、搜索与读文件交替出现时，会把每个操作以近似同等权重呈现。用户第一眼看到的是一面工具卡片墙，而不是任务进展。

核心问题有三类：

- 信息层级太平：处理中、已完成、失败、摘要、日志详情都在抢注意力。
- 扫读成本太高：用户需要逐张卡片读，才能知道任务走到哪里。
- 长列表体感偏重：大量展开详情、日志、搜索结果同时存在时，即使底层性能可控，也会让界面显得卡。

---

## Key Decisions

- **时间轴优先，而不是卡片美化。** 输出区需要成为操作故事线：先看到进展，再决定是否看证据。
- **默认折叠完成节点。** 已完成操作默认只显示一行摘要，避免历史细节持续占用视觉和渲染预算。
- **处理中节点保持展开。** 当前正在发生的动作是第一优先级，应展示状态、即时输出和必要上下文。
- **失败节点高亮且不自动沉没。** 失败是用户最需要看到的异常信号，应在时间轴中保留红色节点、错误摘要和一键展开入口。
- **同类连续操作合并为 operation group。** 连续 read/search/shell 等同类动作先汇总成组，组内详情可展开查看，减少重复标题和状态噪音。

---

## Requirements

### Information Architecture

- R1. 输出区 SHALL 将连续工具调用呈现为纵向时间轴，包含轨道线、状态节点、摘要行和可选详情层。
- R2. 时间轴 SHALL 以“当前进展”作为第一视觉层级，处理中节点默认展开，并使用清晰但克制的 running 状态。
- R3. 已完成节点 SHALL 默认折叠为单行摘要，展示操作类别、对象数量、关键结果和耗时等可扫读信息。
- R4. 失败节点 SHALL 在折叠态也突出显示失败状态、失败原因摘要和关联操作，不依赖用户展开才能发现。
- R5. 详情层 SHALL 作为按需证据层存在，展开后保留原有命令输出、搜索结果、文件列表、diff 或工具详情。

### Grouping

- R6. 连续同类操作 SHOULD 合并为一个 operation group，例如连续读取文件、连续搜索、连续 shell 检查。
- R7. operation group SHALL 显示组摘要，例如“Read 8 files”“Search 3 patterns”“Shell 4 checks”，并保留组内节点数量。
- R8. operation group 展开后 SHALL 允许查看组内单个操作的详情，但默认不把每个子操作都铺满主时间轴。
- R9. 不同类别或状态变化较大的操作 SHOULD 打断分组，避免把语义不同的动作合并到一起。

### Interaction

- R10. 用户 SHALL 能点击摘要行展开/折叠详情层。
- R11. 新出现的处理中节点 SHALL 自动展开；完成后 SHOULD 自动折叠，除非用户手动展开过该节点。
- R12. 用户手动展开的节点 SHOULD 在本轮会话中保持展开，避免界面和用户争夺控制权。
- R13. 时间轴 SHOULD 支持“只看异常/当前”这类低成本过滤或跳转入口，但首版可以只保留视觉 affordance，不做复杂筛选面板。

### Performance Perception

- R14. 默认折叠层 SHALL 避免渲染大型 markdown、日志、diff 和搜索结果详情。
- R15. 详情层 SHOULD 懒渲染或延迟渲染，直到用户展开或节点处于处理中状态。
- R16. 时间轴父层派生 MUST 遵守 live streaming render contract，避免把 heavy grouping、anchors、boundary derivation 重新绑回每个 delta 热路径。
- R17. 长任务中可见节点 SHOULD 优先保持稳定尺寸，避免状态变化引起大幅布局跳动。

### Visual Design

- R18. 时间轴视觉 SHOULD 安静、紧凑、专业，避免大面积卡片、强装饰和高饱和状态色。
- R19. 状态颜色 SHALL 只用于节点、短标签和异常摘要，不在每一行重复铺满。
- R20. 操作摘要 SHOULD 使用强弱两级文本：强文本表达动作和结果，弱文本表达路径、数量、耗时、来源等辅助信息。
- R21. 失败状态 SHOULD 使用更强的边框/背景/节点组合；成功状态只需低调确认。

---

## Scope Boundaries

- 不改变工具调用的底层数据语义。
- 不在首版新增复杂筛选、搜索、批量操作或全局时间轴面板。
- 不把所有历史消息都改成时间轴；本次只聚焦工具调用密集区域。
- 不删除详情内容；只是把详情从默认主视觉层级下沉为按需证据层。
- 不牺牲 live streaming 可见性；当前运行节点仍要及时显示进展。

---

## Success Criteria

- 用户在一屏内能立刻看出当前正在处理的操作、最近完成的一组操作、是否有失败节点。
- 同样数量的工具调用下，默认视图的纵向占用显著减少，目标减少 30% 到 50%。
- 失败节点在快速滚动时仍然可识别。
- 长任务输出的体感更轻：默认不展开大量历史日志和 markdown 详情。
- 深色和浅色主题下都保持清晰层级，并满足 reduced motion 场景。
